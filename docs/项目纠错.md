### 10. 跨数据 CV 被当作可辨识性判据

- 状态：结论已撤回，指标停用。
- 文件：`WORK_STATUS.md` §8 / §10.2、`results/staged_inversion/staged_summary.md`
- 原问题：以四组数据最优参数的变异系数判定
  `G_OH/G_O/scaling_OOH_OH` 为 stable、`k0_1~4` 为 unreliable，并据此写入
  "可以撰写阶段性结论"。
- 根因：CV 在混合参数化下不可比。按 `DEFAULT_PARAM_SPECS` 的实际边界做
  零信息零假设（4 次先验抽样 CV 中位数）：

  | 参数 | 搜索尺度 | 纯先验 CV | 实测 CV | 相对先验收缩 |
  |---|---|---:|---:|---:|
  | G_OH | linear [0.8, 1.8] | 0.187 | 0.068 | 2.8x |
  | G_O | linear [2.2, 3.4] | 0.104 | 0.038 | 2.7x |
  | scaling_OOH_OH | linear [2.8, 3.6] | 0.060 | 0.023 | 2.6x |
  | k0_1~4 | **log10 [-3, 5]** | 1.605 | 1.0-1.7 | **1.0x** |

  `k0` 的 CV 与"完全没有信息"数值上不可区分，因此"k0 因参数补偿而不可靠"
  这一机理解释没有证据支持；三个 stable 参数的收缩倍数几乎相同
  （2.6-2.8x），不像被数据以不同程度约束。CV=0.3 的门槛实际区分的是
  linear 边界与 log10 边界。
- 放大因素：四组数据共用 `seed=42`、共用 `initial_params=base`、共用同一组
  钉住常数，且 `n_forward=50`（8 维空间），优化器基本没离开初值邻域。
- 处置：撤回该结论；可辨识性改由单数据集后验宽度与相关矩阵给出，见
  `docs/superpowers/plans/2026-08-22-low-dim-bonke-model.md`。

### 13. Bonke 2016 引用与实际内容不符

- 状态：文档已更正，模型选择已据此调整。
- 文件：`PROJECT_SUMMARY.md` §4.1、`python/oer_aem/defaults.py`
- 原问题：把 Bonke 2016 当作"预氧化步骤必要性"与 `E0_pre ≈ 1.45-1.50 V`
  的依据。实际上 Bonke 拟合出的是 **E0_eff = 1.9-2.1 V vs RHE、
  k0_cat = 110-325 s^-1**，模型是**1 表面氧化还原 + 1 赝一级催化步的
  3 参数分子催化模型**，不含 AEM 四步；Γ 为 3-11 与 100-110 pmol/cm²。
  项目采用的 1.45-1.50 V 实际来自 Moysiadou 的**直流氧化峰**——DC 峰位与
  FTacV 的 E0_eff 不是同一个量。
- 附带事实：Bonke 明确以 pmol/cm² 量级的超低负载为必要条件（催化直流电流
  足够小，谐波才被表面氧化还原主导）。本项目假定的
  `gamma = 3e-9 mol/cm²` 比之高 30-1000 倍，峰值电流 11 mA，正处于
  Bonke 刻意避开的区间——这与第 14 条的量化噪声底一致。

### 14. 高次谐波信噪比未量化，数值精度投入超出数据信息量

- 状态：未解决（等补充实验）。

  量化台阶 `q = 3.0e-5 A` 对应 `q/sqrt(12) = 8.7 µA`——三组数据的噪声底

  对应谐波信噪比：

  | FT2 | 38.9 | 17.9 | 10.2 | 7.3 |

  | FT4 | 3.9 | 2.5 | 1.9 | 1.6 |

### 19. 拯救者上后台作业随 SSH 断开被销毁（含 tmux）

- 状态：机制已查清；临时绕过可用；根治需用户在 Windows 侧安装常驻会话。
- 现象：2026-08-22 在拯救者启动低维拟合，`nohup ... &` 与
  `tmux new-session -d` 两种方式启动的进程都在 SSH 连接关闭后消失，
  日志停在启动行，无 traceback、无输出文件。
- **首次归因错误，已更正**：最初记为"WSL2 `vmIdleTimeout` 销毁整个 VM"。
  实测否定了这一点：

  | 检查项 | 实测值 | 结论 |
  |---|---|---|
  | 生效的 `.wslconfig` | `C:\Users\lsy.LAPTOP-JBG0SNHL\.wslconfig` | `vmIdleTimeout=86400000`（24 h），不可能是几分钟内销毁的原因 |
  | `logind KillUserProcesses` | `busctl` 读出 `false` | 不是 logind 杀的 |
  | `loginctl show-user lsy` | `Linger=yes` | 停留已开启，不是 linger 缺失 |
  | `uptime` | up 1 day 1:26 | **VM 没有重启** |
  | `who -b` | `system boot 2026-08-22 15:50` | **发行版重启了** |
  | 作业 PID | 113/114/115/116 | PID 命名空间是全新的，佐证发行版重启 |

- 真实根因：WSL2 的 **VM** 与 **发行版（distribution）** 生命周期是两回事。
  `vmIdleTimeout` 管的是 VM。发行版在"启动它的那个会话"退出后会被终止，
  连同该会话派生的所有后台进程一起——`nohup` 与 `tmux` 都在发行版内部，
  发行版一停全部消失。这与 `vmIdleTimeout`、`linger`、`KillUserProcesses`
  都无关，也没有发行版级别的超时开关可调。
- 当前绕过（已验证有效）：正式计算由本机持有一条长连接前台执行：

  ```
  ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=2000 legion \
      'bash /home/lsy/OER-FTAcV-run-<commit>/run_all.sh'
  ```

  连接在，发行版就在。代价是本机必须保持联网且不休眠。
- 根治：在 Windows 上常驻一个 WSL 会话。**用户已于 2026-08-22 安装**
  （`%UserProfile%\oer-wsl-keepalive.vbs` + 启动目录），进程 307/308
  常驻，会话独立于 SSH（sid 307 vs 324）。端到端验证（关掉所有会话后
  发行版仍存活）待当前拟合结束后补做，步骤见
  `docs/legion_environment.md` 第 3 节。
- 追溯提醒：WORK_STATUS §17 记录过"Legion tmux 重算"，说明此前存在某种
  使会话得以保留的条件（例如当时 Windows 上开着一个 WSL 终端）。
  **此前所有声称在拯救者后台完成的长时计算，都应确认其日志确实跑到了
  结尾，而不是中途随发行版一起被销毁。**
