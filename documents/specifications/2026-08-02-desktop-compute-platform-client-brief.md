# OER-FTAcV 桌面计算平台方案任务书（甲方需求）

版本：0.1
日期：2026-08-02
阶段：方案设计与压力测试，暂不实施
使用范围：课题组内部

## 1. 文档用途

本任务书用于约束下一阶段的方案设计。方案方必须先理解现有项目、比较候选
架构并完成压力测试，再提交实施建议。未经甲方批准，不得重写科学核心、迁移
计算语言或开展大规模界面重构。

本阶段回答四个问题：

1. 如何把当前本地网页改造成双击可用的桌面程序；
2. 如何让本地与远程计算通过同一接口运行；
3. 如何保留已经验证的科学代码和证据链；
4. 如何为 HER 及其他反应预留扩展边界，而不过早开发通用平台。

## 2. 甲方背景

OER-FTAcV 当前是碱性 OER 微观动力学、FTacV 信号处理和参数反演项目。
项目已经具备：

- Python 科学核心：物理正演、LSODA/BDF、谐波、lock-in、目标函数、
  敏感性、profile、合成恢复和反演；
- FastAPI 后端与单文件 React/ECharts 前端；
- `oer-wf` 远程计算工作流，可在 Legion WSL 执行、恢复、同步和验收任务；
- MATLAB 参考实现，以及实验性的 C++ 加速后端；
- commit、配置、数据、环境和结果哈希组成的科研证据链。

当前参数优化受计算成本、参数耦合和实验条件限制。甲方希望在不伪造科学进展
的前提下，利用等待实验和长计算的时间改善软件交互、内部使用体验和未来扩展
能力。

## 3. 当前问题

### 3.1 使用体验

当前界面需要启动本地服务并通过浏览器访问。前端的样式、组件和状态逻辑集中
在一个 HTML 文件中，不利于持续维护。甲方需要正常桌面应用的启动和使用体验，
不接受把“手动启动服务并打开本地网址”作为最终入口。

### 3.2 计算位置耦合

项目既有适合本机执行的数据解析、谐波提取、正演和小规模诊断，也有适合
Legion 执行的合成恢复、大规模优化和不确定度计算。远程计算不能成为所有任务
的固定前提，本地计算也不能绕过统一任务和验收契约。

### 3.3 技术路线误判风险

MATLAB App Designer 的界面和内置算法具有参考价值，但界面质量不由计算语言
决定。课题组内部机器不能假定全部安装并授权 MATLAB。因此，不得仅因界面观感
而把已验证的 Python 科学核心整体迁移到 MATLAB。

## 4. 项目目标

方案应支持一个课题组内部使用的桌面计算平台：

- 双击启动，不要求用户手动打开浏览器或启动 Web 服务；
- 桌面界面、科学算法、执行位置和结果验收彼此解耦；
- 本地与远程计算是同等级执行方式；
- Python、C++、MATLAB 等是可替换数值后端，不决定界面架构；
- 保留现有 OER 代码、测试、Gate 和 provenance；
- 后续新增反应时，优先增加反应插件，而不是复制整套应用。

## 5. 非目标

本阶段不要求：

- 编写或打包正式桌面应用；
- 重写 OER 科学核心；
- 把现有 A6 失败改写为算法成功；
- 开发公开 SaaS、账户、计费或多人协作系统；
- 实现所有未来反应的通用机理语言；
- 因方案偏好更改冻结求解器、阈值或正式结果。

## 6. 强制需求

### 6.1 架构边界

方案必须分别定义以下三个维度，不得混为同一配置：

| 维度 | 示例 |
|---|---|
| 反应模型 | OER、未来 HER、其他反应 |
| 数值后端 | Python LSODA/BDF、C++、可选 MATLAB |
| 执行位置 | 本机、Legion、未来其他计算节点 |

界面不得直接依赖 SSH 命令、WSL 路径、MATLAB 对象或具体 ODE 实现。

### 6.2 统一计算接口

本地和远程执行至少应具有一致的能力语义：

```text
capabilities → submit → status → cancel → fetch_results → verify
```

方案方可以调整接口名称，但必须说明输入、输出、状态机、异常、取消语义和结果
归属。远程 Provider 可以复用 `oer-wf`；本地 Provider 必须使用独立计算进程，
不得让长计算阻塞界面进程。

### 6.3 任务与结果契约

相同科研任务在本地和远程必须共享：

- TaskSpec 或等价的版本化任务描述；
- 参数、数据、随机种子、求解器和 worker 配置；
- 状态、失败分类和结果 schema；
- validator 和科学 Gate；
- commit、配置、输入、环境和输出 provenance。

执行位置或后端不得静默切换。自动推荐可以存在，但提交前必须由用户看到并
确认最终配置。

### 6.4 桌面体验

方案必须实现或明确规划：

- 双击启动和正常退出；
- 无外网时仍能加载主界面，禁止依赖运行时 CDN；
- 数据、参数、运行配置、进度、日志摘要和结果之间的清晰导航；
- 运行中界面可继续浏览，任务可取消且关闭窗口时给出明确选择；
- 重新启动后能够恢复任务视图，不把“界面关闭”等同于“计算失败”；
- 科学结果明确显示结论等级、适用范围和未通过的 Gate；
- 图表可导出，且导出内容保留单位、图例和必要 provenance。

### 6.5 MATLAB 边界

- MATLAB 可以作为参考实现、算法对照或可选后端；
- 正式应用不得要求每台机器安装 MATLAB；
- 方案必须说明无 MATLAB 时的完整可用路径；
- 若建议 MATLAB Engine、Runtime 或编译组件，必须列明许可证、平台、打包、
  CI 和结果复现成本；
- 不得仅凭某个 MATLAB 页面更美观或存在内置优化器，就建议迁移科学核心。

### 6.6 内部部署与安全

- 首版仅面向课题组内部，不引入公开云服务；
- SSH 私钥、密码、token 和代理信息不得打包进应用或写入结果；
- 远程连接使用现有 SSH 别名或系统凭据机制；
- 方案必须给出 macOS 控制端与 Legion WSL 的支持方式，并评估 Windows
  本地桌面版本的代价；
- 安装、升级和回退流程必须可审计。

## 7. 候选方案要求

方案方至少比较以下路线，不得只提交单一偏好：

1. React/ECharts + Tauri 桌面壳 + Python 计算进程；
2. PySide6/Qt 原生 Python 桌面应用；
3. MATLAB App Designer 或 MATLAB Runtime 路线，作为受许可证约束的备选。

允许提出第四种路线，但必须使用相同评价口径。比较至少覆盖：

- 界面质量和开发效率；
- 本地、远程和混合计算；
- macOS/Windows 打包；
- Python/C++/MATLAB 后端接入；
- 安装包大小、启动时间和内存；
- 测试、CI、版本升级和故障诊断；
- 许可证与长期维护；
- 对现有代码的迁移量和回归风险。

甲方当前倾向 React/ECharts + Tauri，但该倾向不是结论。方案方应通过证据确认
或否决。

## 8. 压力测试要求

方案报告必须逐项给出测试方法、预期结果、失败判据和缓解措施。

| 场景 | 必须回答的问题 |
|---|---|
| 无外网启动 | CDN、字体或资源不可用时，主界面能否完整加载？ |
| 无 MATLAB | 是否仍能完成所有基础 OER 操作和正式结果查看？ |
| 本地长计算 | 65,536 点轨迹和多 trial 运行时，界面是否卡死或丢失状态？ |
| 关闭并重开 | 计算继续、停止或失败的语义是否明确，任务能否重新发现？ |
| 远程断连 | SSH 中断、WSL 重启或状态冲突时，能否区分运行、失败和未知？ |
| 本地/远程一致性 | 同一 TaskSpec 的结果 schema、validator 和数值容差是否一致？ |
| 后端失败 | ODE、数值、结构、基础设施和科学失败是否被正确分层？ |
| 任务取消 | 是否避免残留进程、半写结果被误判为成功或正式证据被覆盖？ |
| 并发任务 | 多任务是否竞争 CPU、BLAS 线程、输出目录或状态文件？ |
| 升级回退 | 新桌面版本能否读取旧任务和结果，失败后能否回退？ |
| 凭据安全 | 安装包、日志、崩溃报告和结果中是否泄露凭据？ |
| 第二反应 | 加入最小 HER 示例时，哪些模块需要修改，是否暴露错误抽象？ |

不得用界面演示代替故障注入，不得用 smoke 结果代替科学 validator。

## 9. 本阶段交付物

方案方应提交：

1. **现状审计：** 现有 Web、Python、MATLAB、C++ 和 `oer-wf` 的可复用边界；
2. **候选方案比较：** 至少三条路线及可核查依据；
3. **推荐架构：** 组件、接口、数据流、状态机和错误处理；
4. **界面方案：** 核心用户路径、信息架构、至少三个关键页面线框图、视觉
   规范和科学结论等级的呈现方式；
5. **原型范围：** 最小可验证桌面原型包含什么、不包含什么；
6. **迁移计划：** 分阶段改动、兼容策略、回退点和每阶段验收门；
7. **压力测试报告：** 覆盖第 8 节全部场景；
8. **风险登记：** 科学、数值、工程、许可证、安全和维护风险；
9. **工作量估算：** 按阶段列出，不以未经测量的精确工时冒充事实；
10. **甲方决策清单：** 只保留确实影响实施范围的选择。

交付物必须区分事实、实测结果、推测和建议。未经运行或查证的性能、兼容性和
许可证信息必须标注“待验证”。

## 10. 方案阶段验收标准

满足以下条件后，甲方才考虑批准实施：

- 三条候选路线使用同一评价矩阵；
- 推荐方案没有把 MATLAB 变成强制依赖；
- 本地与远程计算通过统一接口表达，但失败和资源特性没有被抹平；
- 没有要求迁移已验证的科学核心才能完成桌面原型；
- 界面方案覆盖数据导入、计算任务和结果分析三个关键用户路径；
- 状态机覆盖运行、成功、取消、基础设施失败、数值失败和科学失败；
- 压力测试包含可执行步骤和明确失败判据；
- 方案具有最小原型、回退点和停止条件；
- 后续 HER 扩展用于检验抽象，不作为首版开发范围膨胀的理由。

## 11. 否决条件

出现以下任一情况，方案应退回修改：

- 以界面观感为理由整体重写科学代码；
- 把本地网页套壳但仍要求用户手动启动服务；
- 把 Legion、SSH 或 WSL 细节写入界面业务组件；
- 本地和远程产生无法统一验证的结果格式；
- 自动切换求解器、执行位置或参数而不留痕；
- 将 `PASS` 界面状态替代独立 validator；
- 将当前参数恢复瓶颈描述为已经通过更换 UI 或语言解决；
- 未验证即宣称跨平台、离线可用或数值等价。

## 12. 后续执行顺序

```text
甲方任务书
→ 现状审计
→ 候选方案与推荐设计
→ 书面压力测试
→ 最小技术原型和故障注入
→ 甲方评审
→ 实施计划
→ 分阶段开发
```

当前 A6-v2 正式计算和验收不因本任务中断。桌面平台方案不得修改该任务已经
冻结的代码、配置、后端和证据。
