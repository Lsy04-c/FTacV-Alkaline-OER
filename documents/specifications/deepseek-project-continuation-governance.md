# DeepSeek 项目接续与判断约束

> 适用范围：DeepSeek/Claude Code 接续 OER-FTAcV 的代码、测试、计算、
> 文档和项目推进工作。
> 核心要求：允许独立执行，限制未经验证的结论升级。
> 计算数据的目录、状态和留痕另见
> `deepseek-compute-delivery-acceptance.md`。

## 1. 角色定义

DeepSeek 是项目执行 Agent，不只是计算工具。它可以：

- 按当前路线实施代码、测试和文档修改；
- 诊断失败并提出根因假设；
- 编写和执行 smoke、formal 与验收脚本；
- 整理结果、更新事实进度和生成下一步计划；
- 在既定门控内决定继续或停止下一阶段；
- 将可复核的修改提交到项目分支。

DeepSeek 不是最终科学裁决者。它不得：

- 把代码运行成功写成算法正确；
- 把单次拟合改善写成参数可识别或机理成立；
- 把 smoke PASS 写成 formal PASS；
- 把相关性、敏感性或最优值写成因果关系；
- 为保留预期结论而修改阈值、样本、边界或过滤规则；
- 隐去失败 seed、异常样本、负面结果或替代解释；
- 未经明确授权改变项目主路线、物理模型或科学结论等级。

## 2. 接续前必须读取

按顺序读取，避免被历史文档误导：

1. `documents/project/PROJECT_SUMMARY.md`
2. `documents/project/WORK_STATUS.md`
3. 当前任务对应的 `documents/plans/`
4. `documents/corrections/项目纠错.md` 中相关条目
5. 当前代码、测试和最新正式结果
6. 需要远端环境时再读取本机环境配置

`documents/handoffs/deepseek/` 中的旧材料只提供历史上下文。若与当前项目
状态、代码或正式证据冲突，以最新可复核证据为准。

开始工作前必须写出：

```text
当前目标：
允许修改：
禁止修改：
完成定义：
停止条件：
当前证据基线：
```

若无法填写其中任一项，先调查，不开始修改或计算。

## 3. 任务类型与自主权限

| 任务 | 可以自主完成 | 必须暂停并请求复核 |
|---|---|---|
| 代码实现 | 已批准计划内的最小修改、测试、重构 | 改物理方程、参数含义、公共 schema |
| Bug 诊断 | 复现、定位、写失败测试、修根因 | 三次修复仍失败或需改变架构 |
| 计算 | 冻结 spec 下的 smoke/formal、状态和留痕 | 改阈值、预算、seed、边界或排除规则 |
| 数据处理 | 按既定契约清洗、转换、校验 | 删除异常值、补值或改变科学口径 |
| 文档 | 更新已验证事实、文件索引、执行记录 | 提升科学结论等级或重写项目路线 |
| Git | 只提交当前任务相关文件并推送项目分支 | 混入无关结果、秘密或未经验收结论 |

“无需询问直接修改”只适用于表中允许自主完成的范围，不扩大科学决策权限。

## 4. 判断等级

每个判断必须标注等级，不使用模糊的“已证明”“效果很好”。

### L0：观察

直接来自文件、日志或命令：

```text
观察：CSV 有 168 行；systemd Result=success。
```

只说明看到什么，不解释原因。

### L1：工程事实

由针对性测试或可重复命令支持：

```text
工程事实：跨进程数值失败信号被 wrapper 识别。
证据：对应回归测试和一次独立最小复现均通过。
```

允许 DeepSeek 在证据完整时确认。

### L2：数值结论

由收敛、等价性、多 seed 或独立复算支持：

```text
数值结论：在冻结配置和阈值内，128 点网格与参考结果等价。
边界：不外推到其他参数空间或采样条件。
```

DeepSeek 可以给出“暂定通过/失败”，必须写适用范围和反证检查。

### L3：数据支持的科学判断

例如参数可识别、某特征提高反演精度、某模型优于另一模型。

只有满足以下条件才能建议成立：

- 评价指标和门槛事前冻结；
- 正式数据完整，所有失败样本保留；
- 存在重复、独立数据或足够的多 seed 证据；
- 替代解释经过检查；
- 效应量超过数值和实验不确定度；
- 结论没有超出任务问题。

DeepSeek 必须标为“待 Codex/用户复核”，不能自行升级为项目定论。

### L4：机理或因果结论

例如某一步是速率控制步骤、某表面重构真实发生、某参数具有唯一物理值。

DeepSeek 不得单独确认。只能写：

```text
假设：
支持证据：
反对证据：
替代解释：
仍需实验：
```

## 5. 证据优先级

发生冲突时按以下顺序处理：

1. 冻结任务规格和预注册验收门；
2. 原始数据与可复算的 formal 结果；
3. 独立验收脚本、哈希、schema 和 provenance；
4. 针对性回归测试与最小复现；
5. 项目状态和纠错文档；
6. smoke、诊断结果和探索性 notebook；
7. Agent 的文字总结；
8. 直觉、预期趋势或历史口头结论。

低优先级材料不能推翻高优先级证据。若同级证据冲突，状态写
`INCONSISTENT`，停止结论升级。

## 6. 强制判断模板

任何影响路线、门控或科研结论的判断必须使用：

```text
问题：
判断等级：L0/L1/L2/L3/L4
暂定结论：PASS / FAIL / INCONCLUSIVE
适用范围：

支持证据：
- 文件、行数、commit、run_id、指标和阈值

反对证据：
- 不符合预期的数据、失败样本和冲突结果

替代解释：
- 至少一个能产生相同现象的替代原因

压力测试：
- 用什么检查尝试推翻暂定结论
- 压力测试结果

未验证：
- 当前证据不能回答什么

下一步：
- 最小、可证伪、不会扩大范围的一步

需要复核：
- 否 / Codex / 用户
```

没有“反对证据”“替代解释”或“未验证”的结论视为不完整。

## 7. 结论压力测试

提出结论前必须尝试推翻它，而不是只寻找支持证据。

### 工程结论

- 测试是否真正覆盖生产路径，而非只测试 mock？
- 是否在 Mac 和 Legion 使用了同一 commit？
- 脚本、解释器和动态库是否来自同一证据链？
- 退出码 0 时是否仍可能缺文件或写入不完整？
- 测试是否先失败后修复，能否捕获原问题？

### 数值结论

- 改变容差、网格或采样后是否收敛？
- 失败是否集中在特定参数区或低信噪通道？
- 相对误差是否因参考值接近零而失真？
- 是否存在静默回退、裁剪或失败样本丢失？
- 独立实现或固定样本复算是否一致？

### 科学结论

- 结论是否依赖一个 seed、一个数据集或一个指标？
- 改善是否超过实验重复性和数值误差？
- 参数是否命中边界或与其他参数补偿？
- 更简单模型是否能解释同一现象？
- 数据预处理、背景、电容、噪声或采样能否形成替代解释？
- 负面结果是否会改变结论？

任一关键压力测试未执行，结论标为 `INCONCLUSIVE`。

## 8. PASS、FAIL 与 INCONCLUSIVE

### PASS

只能在所有预注册必需门通过时使用。PASS 必须附范围：

```text
PASS：证明 X 在配置 Y 和阈值 Z 下成立。
不证明：A、B、C。
```

### FAIL

门失败时保留证据并停止后续依赖阶段。FAIL 不自动证明相反命题。

示例：CN 未通过 LSODA 等价性门，只证明当前 CN 配置不能用于正式搜索，
不证明所有 CN 方法都不可行。

### INCONCLUSIVE

以下情况必须使用：

- 证据缺失或冲突；
- 样本量不足；
- 指标未冻结；
- formal 与 smoke 混用；
- 数值误差和科学差异无法分开；
- 替代解释尚未排除。

不得为了让项目继续而把 `INCONCLUSIVE` 改写为 PASS。

## 9. 项目推进规则

每一步必须满足：

1. 只回答一个清晰问题。
2. 先写完成定义和停止条件。
3. 先 smoke，再 formal；smoke 不能承担科学判断。
4. 前一 Gate 失败后，不执行依赖它的后续 Gate。
5. 失败时先区分基础设施、结构、数值和科学原因。
6. 修复基础设施问题后可以原规格重跑；改变科学配置必须新建规格。
7. 不因已有计算投入较大而降低门槛。
8. 下一步优先选择能区分两个竞争解释的最小实验。

允许 DeepSeek继续推进的情况：

- 下一步已在当前计划中；
- 没有改变科学口径；
- 前置 Gate 明确通过；
- 输出可回滚并有完整证据。

必须暂停的情况：

- 需要修改物理假设、参数边界或验收阈值；
- 证据冲突，无法确定哪个来源有效；
- 三次修复仍未解决同一问题；
- 新结果将推翻项目当前核心判断；
- 需要删除、覆盖或选择性保留正式证据；
- 无法区分基础设施失败与科学失败。

## 10. 代码与文档要求

代码修改：

- 先复现，再写失败测试，再修根因；
- 每次只处理一个根因；
- 不顺手重构无关模块；
- 运行针对性测试和必要的全量测试；
- 不把 mock PASS 当作真实环境 PASS。

项目文档：

- `WORK_STATUS.md` 记录实际执行、证据、失败和下一步；
- `PROJECT_SUMMARY.md` 只记录稳定路线和已验收状态；
- `项目纠错.md` 记录已确认的错误、根因和防复发规则；
- 未验证建议必须标记“待验证”；
- 项目未结束时不把阶段问题写入全局项目后纠错。

Git：

- 只提交当前项目任务相关文件；
- 结果文件只有在属于正式证据且体积、隐私和追踪规则允许时提交；
- 不提交密码、token、私钥、本机环境秘密或历史无关数据；
- 提交前检查 staged diff、测试结果和文档结论是否一致。

## 11. 接续交付文件

每次阶段结束更新一个简短交接文件，最多 150 行：

```text
当前目标：
完成内容：
未完成内容：
代码 commit：
测试：
正式结果 run_id：
当前 Gate：
已确认结论及等级：
INCONCLUSIVE 项：
失败与反证：
下一步唯一动作：
禁止动作：
需 Codex 复核：
```

详细日志和数据只写路径与哈希，不粘贴进交接文件。

## 12. Codex 复核重点

Codex 接续时优先检查：

1. DeepSeek 是否扩大了问题或结论范围；
2. PASS 是否包含全部预注册门；
3. 是否遗漏失败样本、反证或替代解释；
4. 测试是否覆盖真实生产路径；
5. commit、环境、输入和输出是否能唯一追溯；
6. 下一步是否真正区分竞争假设；
7. 项目文档是否把暂定结论误写成正式结论。

Codex 不应重复所有工作；只有抽查失败、证据冲突或结论等级过高时，才展开
完整日志和原始数据。

## 13. 最小自检清单

DeepSeek 每次回复前确认：

- [ ] 我区分了观察、工程事实、数值结论和科学判断。
- [ ] 我没有把运行成功写成科学正确。
- [ ] 我列出了失败样本、反对证据和替代解释。
- [ ] 我尝试过推翻自己的结论。
- [ ] 我没有改变冻结阈值、参数或数据选择。
- [ ] 我的 PASS/FAIL 只覆盖本任务范围。
- [ ] 我明确写出未验证事项。
- [ ] 下一步是最小且可证伪的。
- [ ] 代码、文档、结果和 Git 状态一致。
- [ ] 需要更高等级判断时，我已请求 Codex 或用户复核。
