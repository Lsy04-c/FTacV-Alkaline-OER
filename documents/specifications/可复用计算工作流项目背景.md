# 可复用计算工作流项目背景

## 一、背景

OER-FTAcV 项目已经形成“本地开发、GitHub 固化版本、拯救者执行长计算、
Mac 验收和归档”的基本流程。随着验证阶段增加，同一套工程操作在求解器
等价性、敏感性分析、合成恢复和参数 profile 等任务中反复出现。

这些重复操作本身不产生新的科研判断，却持续占用人工操作时间和 agent
对话额度。部分操作还涉及 Mac、Windows、WSL、systemd 和 Git 多个环境，
手工拼接路径与命令容易造成工作树混用、输出目录错误、日志漏查和结果
provenance 不完整。

因此需要建立一套可复用的计算工作流，把稳定、重复、可验证的工程步骤
整理为模板或脚本。工作流的目标不是替代科研决策，而是减少重复操作，
统一证据格式，并让每次计算更容易复现和审计。

## 二、目前重复出现的操作

### 1. 计算前环境确认

每次正式计算前都需要重复确认：

- Mac 与拯救者的项目位置；
- SSH、WSL 和 systemd 是否可用；
- Python、依赖和动态库来源；
- Git commit、工作树状态和远端分支；
- 计算脚本与输出目录是否属于同一版本。

这些步骤的检查内容基本固定，适合由统一入口完成。

### 2. 精确版本工作树准备

正式计算通常需要：

- 推送当前验证版本；
- 在拯救者拉取对应 commit；
- 创建 commit 专属 worktree；
- 检查工作树是否干净；
- 防止不同 worktree 的脚本、环境和结果混用。

该流程重复频率高，而且路径错误会直接破坏结果的可复现性。

### 3. Smoke 与正式计算衔接

不同任务都遵循相似过程：

1. 用小规模任务检查脚本能否运行；
2. 验收 smoke 的 schema、关键参数和 provenance；
3. 使用相同科学配置启动正式计算；
4. 为正式结果创建唯一目录。

目前这些步骤分散在不同命令中。smoke 有时缩小了不应改变的关键参数，
导致未覆盖正式计算中的真实故障。

### 4. 长计算启动和状态判断

拯救者上的正式任务通常使用 systemd。重复操作包括：

- 设置 worker 和 BLAS 线程；
- 指定工作目录、解释器、脚本和日志；
- 启动唯一名称的服务；
- 检查进程、退出状态和 journal；
- 区分仍在运行、正常完成和异常退出。

仅凭进程消失或输出目录存在不能判断任务成功。该判断规则应统一。

### 5. 结果同步

正式结果完成后，需要从 WSL 同步到 Mac。该过程会重复处理：

- Windows 默认 shell 与 WSL 路径差异；
- `rsync` 在远端 shell 中不可用的问题；
- 唯一输出目录；
- 同步前后文件数量和哈希；
- 避免覆盖历史证据。

这些操作适合封装为稳定的传输流程。

### 6. 通用结果验收

不同科学任务虽然指标不同，但都要检查：

- 预期文件是否齐全；
- 表格 schema、行数、样本数和分组是否正确；
- 数值是否有限；
- solver 状态和失败次数；
- commit、dirty 状态、环境和完整配置；
- manifest 中的 SHA256 是否与文件一致。

这部分属于通用工程验收，可以复用。具体科学阈值仍应由任务单独定义。

### 7. 项目记录与 Git 操作

每个验证阶段结束后通常需要：

- 更新项目目标、状态、计划和纠错记录；
- 运行相关测试和全量测试；
- 排除 smoke、无效历史结果和无关文件；
- 分阶段提交并推送 GitHub。

其中测试、文件范围检查和 Git 状态检查可以标准化；科研结论的文字更新
不应完全自动生成。

## 三、需要脚本化的部分

建议优先脚本化以下工程流程：

1. 环境和连接的只读检查；
2. commit 专属 worktree 的准备与验证；
3. smoke 任务的启动和结构验收；
4. systemd 正式任务的启动、状态和日志检查；
5. WSL 到 Mac 的结果同步；
6. 文件、schema、有限值、哈希和 provenance 的通用验收；
7. 测试执行、Git 变更范围检查和交付清单生成。

这些流程输入明确、判断规则稳定，自动化风险较低。

## 四、不应直接自动化的部分

以下内容必须保留科研判断：

- 是否修改物理模型；
- 是否接受或调整科学阈值；
- 参数应归类为自由、固定、窄先验或 diagnostic-only；
- Scientific FAIL 是否需要新实验、缩减参数或更换算法；
- smoke 是否足以覆盖正式任务的科学风险；
- 是否进入下一阶段正式计算；
- 如何解释异常、耦合和不确定性。

脚本可以整理证据和计算指标，但不能自动宣布科学结论。

## 五、总体解决方向

### 1. 统一任务描述

为每类计算建立简洁的任务配置，记录 commit、运行脚本、参数、输出目录、
worker、预期文件和验收器。后续启动任务时只需替换任务配置，不再重复
拼接完整命令。

### 2. 建立统一工作流入口

使用一个轻量级 Python 工作流入口组织准备、smoke、启动、查询、同步和
验收。Python 更适合处理 JSON、路径、哈希和跨平台状态，主流程不再依赖
复杂的多层 shell 引号。

### 3. 通用验收与任务专用验收分离

通用验收负责文件、schema、有限值、哈希和 provenance。不同计算任务保留
各自的科学验收器，例如求解器等价性、合成恢复和 objective profile。

### 4. 明确失败类型

工作流应把失败至少分为：

- 环境或连接失败；
- 启动和传输失败；
- 输出结构或 provenance 失败；
- 数值求解失败；
- 科学门控失败。

基础设施失败不得写成 Scientific FAIL，科学失败也不得通过修改阈值变成
工程 PASS。

### 5. 保留完整证据链

每次正式任务使用唯一输出目录，并保留 commit、环境、配置、命令、日志和
哈希。失败结果不覆盖，便于后续纠错和复盘。

### 6. 分阶段实施

第一阶段只实现环境检查、worktree、smoke、systemd、同步和通用验收。
第二阶段增加不同计算类型的专用验收器。文档更新、科学决策和 Git 提交
暂时保留人工确认，避免自动化范围过大。

## 六、预期收益

完成该工作流后，预计可以：

- 减少重复命令和对话额度消耗；
- 降低跨平台路径和引号错误；
- 提前发现正式配置才会触发的问题；
- 统一结果目录和 provenance；
- 缩短从计算完成到验收、同步和归档的时间；
- 让其他 agent 更容易接手项目；
- 将 agent 的主要用量集中在科研设计、异常解释和路线决策上。

## 七、当前建议

优先建设轻量级 Python 工作流，不引入大型工作流平台。先覆盖高频、稳定、
低风险的工程操作，再根据后续任务数量决定是否扩展。任何自动化都应遵循
“工程步骤可复用，科学判断不自动化”的边界。
